호스트가 검토한 파일 선택과 작업공간 설정을 처리한다. 수동 복사나 사용자 작성

| 상황 | 실제 처리 |
| --- | --- |
| 처음 시작하는 비어 있거나 없는 작업공간 | 검토한 파일을 읽어 검증하고 독립 복사본·해시 기록을 생성 |
| 승인된 기존 Peekly 파일럿 폴더 | 고정된 64개 코드 파일과 정확한 결과 참조만 읽고 기존 Library·QA 검증기로 재사용·보고 |

| 준비 도중 중단 | 미완료를 표시하고 같은 명령으로 검증된 파일부터 이어서 준비 |

| 저장된 실패·판정 보류 결과 | 상태와 시도 수를 보존해 이전 결과로 표시. 새 실행이나 통과를 생성하지 않음 |

일반 파일 준비 경로는 임의의 저장 메타데이터를 자동으로 가져오지 않는다.
기존 근거를 자동 연결하는 현재 어댑터는 승인된 Peekly 고정 복사본 범위다.
다른 제품의 목표·페르소나·실제 실행 경로는 호스트가 기존 스킬 흐름으로 검토한다.
이 구현은 범용 제품 실행기나 자동 페르소나 생성기를 가장하지 않는다.

## 재사용한 기존 구현

새 모델 호출·설치기·브라우저 실행기를 만들지 않았다.

- 기존 argparse CLI와 배포 런처에 진입점을 연결했다.
- Library의 버전·지문·현재 PRD·검토 기한 검사를 그대로 사용했다.
- swarm의 receipt·과거 시도·요구사항별 보고 검사를 그대로 사용했다.
- Store 잠금, canonical 해시, atomic 저장과 배포·소스 안정성 검사를 재사용했다.
- 파일 복사만 명시한 상대 경로에 대한 descriptor 기반 no-follow 읽기로 보완했다.
  외부 프레임워크나 새 의존성은 추가하지 않았다.

기존 insane-search는 외부 연구 수집용이며 이 로컬 준비 문제의 해결에 필요하지 않았다.
디시·유튜브 등 접근이 제한된 외부 경로, 실계정, 유료 API, 모델 실행은 사용하지 않았다.

## 기존 페르소나와 결과 보존

새 작업공간과 새 CLI 프로세스에서 기존 페르소나의 정확한 지문과 버전을 재확인했다.

| 페르소나 | 재사용 revision |
| --- | --- |
| PER-EXPLORE | 1 |
| PER-RETURN | 1 |
| PER-ARCHIVE | 1 |
| PER-KEEP | 2 |

새 revision을 가져오거나 생성하지 않았다. 원본 Library/실행의 lock·state를 변경하지 않고
개인 작업공간의 사본에서 기존 검증기를 실행했다. PRD·빌드 참조는 승인된 원래
고정 복사본과 계속 연결되므로, 그 입력이 바뀌거나 없어지면 검증을 중단한다.

이전 결과는 **실패 1 · 판정 보류 4 · 통과 0**이다. T-LARGE의 두 시도와 실패 기준,
근거 해시를 보존했다. 보고서에는 내부 과제 ID보다 사용자 목표를 먼저 표시한다.

새 Peekly 사용자 여정 실행 횟수는 **0**이다. 원래 실패를 재현 성공이나 실사용자 효과로
바꾸지 않았다. 기존 대량 입력 결함은 해결되지 않았으며 Peekly 제품 코드는 수정하지 않았다.
원래 고정 복사본과 결과 등 183개 파일의 해시가 작업 전후 일치했다.
이 수치는 node_modules를 제외한 승인된 이전 실험 범위이며,
외부에서 바뀐 원본 PaywallModal 또는 원본 233개 파일 전체의 불변을 주장하지 않는다.
이번 작업은 원본 Peekly 체크아웃을 쓰지 않았다.

## 회귀·복구·권한 경계

새 회귀 24개가 통과했다. 빈 폴더, 일반 제품의 검토 파일 선택, 실제 Library/receipt 재사용,
누락 입력 안내, 같은 입력 반복, 중단된 복사 재개, 복사 중 원본 변경, 수정된 사본 보존,
다른 파일이 있는 목적지와 중첩 경로 거부, 두 호출의 경쟁을 검사했다.

상위 경로 이동, 심볼릭 링크와 부모 링크, 하드링크, FIFO, 큰 파일, 키 모양의 내용,
외부 PRD/빌드/근거 경로, 만료된 페르소나, 변조된 근거, 진행 중 과제,
다른 사용자가 쓸 수 있는 목적지도 검사했다. 폴더 권한을 자동 변경하지 않았다.
키 검사와 파일 목록은 범위 제한 장치이며 모든 개인정보를 판별하는 인증이나
임의의 적대적 코드를 격리하는 OS 샌드박스가 아니다. 호스트의 내용 검토가 필요하다.

실제 64개 고정 복사본을 사용한 별도 준비 검증에서는 다음을 확인했다.

- 기존 benchmark `prepare --source ... --work ...`가 처음 쓰는 빈 폴더에서 완료됐다.
- 반복 실행과 별도 `status`가 같은 보고를 반환했다.
- 파일 5개 뒤 제어된 예외로 중단했을 때 준비 완료로 보고하지 않았다.
- 같은 명령으로 재개한 뒤 그 5개 파일의 바이트와 수정 시각이 유지됐다.
- 두 독립 CLI 프로세스의 동시 시작이 모두 종료 코드 0으로 완료됐다.
- ZIP을 추출한 배포본을 다른 작업 디렉터리에서 실행해 같은 준비·재사용·보고가 완료됐다.

## 보존한 실패와 미검증 범위

기존 빈 폴더 prepare는 종료 코드 1로 재현됐다.

일반인 usability study, 전환율·만족도·페르소나 우위는 이번에 해결하거나 검증하지 않았다.
